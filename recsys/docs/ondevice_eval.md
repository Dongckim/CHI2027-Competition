# 온디바이스 경량 모델 평가 노트

11/7 회의에서 정한 대로, 추천 모델을 폰에서 서버 없이 돌아가게 줄이고 그 결과를 기존 서버 모델과 비교했다. 여기 숫자는 `docs/ondevice_report.json`, `docs/light_report.json`, `docs/relevance_report.json`에서 나왔고, 맨 아래 명령으로 다시 만들 수 있다.

## 무엇을 줄였나

폰에서 실제로 도는 모델은 질문을 벡터로 바꾸는 질문 인코더 하나다. 논문 벡터, 키워드 색인(BM25), 클러스터, 요약은 모두 미리 계산해 둔 데이터라서 폰은 찾아보기만 한다. 그래서 줄일 대상은 질문 인코더, 논문 벡터, 그리고 이것을 돌리는 실행 환경이었다.

| | 서버 모델 | 폰 모델 v1 (10/5) | 폰 모델 v2 (이번) |
|---|---|---|---|
| 질문 인코더 | 파인튜닝 bge-m3, 2,288 MB | bge-small 12층 트랜스포머, int8 34 MB | 트랜스포머 없음: 단어 조각마다 int8 벡터 하나, 평균 내고 작은 행렬 하나, 8.0 MB |
| 논문 벡터 | 1,024차원 float32, 11.4 MB | 같은 것 두 벌, 21.7 MB | 128차원 int8, 0.37 MB |
| 실행 환경 | GPU 서버 + 네트워크 | onnxruntime-web (WebAssembly 14 MB) | 없음 (JavaScript만, 토크나이저 36 KB) |
| 질문 하나 처리 | GPU에서 인코딩만 22 ms + 네트워크 | 인코딩 약 6 ms (CPU 1스레드) | 인코딩 0.1 ms, 추천 전체 1.2–1.7 ms (Python) |

폰이 처음에 내려받는 전체 파일(모델, 벡터, 프로그램 데이터, 실행 코드)은 83 MB(gzip 49 MB)에서 20 MB(gzip 10 MB)로 줄었다. 이번에 새로 들어간 한 줄 요약과 질문 데이터까지 포함한 크기다.

줄이는 방법은 GPU에서 여러 개를 학습해 보고 골랐다. 트랜스포머 층을 12층에서 6·4·3층으로 줄인 것, 트랜스포머를 아예 빼고 단어 벡터만 남긴 정적 모델(256차원, 384차원), 그리고 논문 벡터 차원을 1,024에서 512·256·128로 줄인 것을 모두 같은 조건으로 비교했다. 논문 벡터는 128차원 int8까지 줄여도 정확도가 그대로였다. 정적 모델은 의미 점수가 약해지는 만큼 키워드 점수의 비중을 0.5에서 1.0으로 올리니 차이가 많이 줄었다. 6층 트랜스포머(23 MB)가 정확도는 조금 더 높았지만 실행 환경 14 MB가 같이 필요해서, 실행 환경이 아예 필요 없는 정적 모델을 골랐다.

## 서버 모델과 정확도 비교

학습 때 한 번도 보지 않은 논문의 질문 750개로 쟀다. R@1은 정답 논문이 1등인 비율, R@8은 상위 8개 안에 드는 비율이다. 모두 키워드 점수와 합친 최종 점수 기준이다.

| 모델 | 크기 | R@1 | R@8 |
|---|---|---|---|
| 서버: 파인튜닝 bge-m3 | 2,288 MB, GPU | 0.803 | 0.964 |
| 서버: 원본 bge-m3 | 2,288 MB, GPU | 0.784 | 0.948 |
| 폰 v1: 12층 트랜스포머 | 34 MB | 0.776 | 0.959 |
| **폰 v2: 정적 모델** | **8 MB** | **0.769** | **0.945** |
| 키워드(BM25)만 | 0 | 0.773 | 0.927 |

폰 v2는 서버 모델보다 R@1이 3.4%p, R@8이 1.9%p 낮고, 원본 bge-m3 서버와는 비슷하다. 크기는 서버의 0.35%다. 키워드만 쓸 때와 비교하면 R@1은 비슷하지만 R@8이 1.8%p 높아서, 단어가 달라도 뜻이 비슷한 논문을 끌어오는 몫은 여전히 한다.

## 같은 요청에 같은 결과가 나오나

배포하는 모델 그대로, 연구 질문 51개에 대해 추천 결과와 하루 루트(6개 정류장, 5일, 루트 255개)를 서버 모델과 폰 모델로 각각 만들어 비교했다.

| | 결과 |
|---|---|
| 추천 상위 8개가 겹치는 비율 | 75% |
| 1등이 같은 비율 | 86% |
| 루트 정류장이 같은 수 (6개 중) | 평균 3.4개 |
| 폰 루트의 질, 서버 점수 기준 | 서버 루트의 96.7% (하위 10%도 90%) |

루트는 정류장 절반 정도가 다르다. 1등부터 시간에 맞춰 채우는 방식이라 점수가 조금만 달라도 그 뒤 선택이 연쇄적으로 바뀌기 때문이다. 그래서 폰이 고른 정류장을 서버 모델의 점수로 다시 매겨 봤는데, 서버 자신이 고른 루트의 96.7% 수준이었다. 다른 발표를 고르더라도 서버가 보기에 거의 비슷하게 맞는 발표로 채운다는 뜻이다.

## 경량화하면서 같이 고친 것

정적 모델은 "CHI가 다루지 않는 주제"를 잘 못 알아봤다. 단어 벡터를 평균 내다 보니 흔한 단어 때문에 어떤 질문이든 가장 가까운 논문과의 코사인이 0.4 근처로 나왔다. 그래서 가장 높은 코사인 하나만 보던 판정을, 폰이 이미 가진 신호 다섯 개(가장 높은 코사인, 20등과의 차이, 가장 높은 키워드 점수, 질문 단어 중 프로그램에 있는 단어의 비율, 그 단어들이 얼마나 드문지)로 판단하는 작은 로지스틱 회귀로 바꿨다. 학습에는 HCI가 아닌 40개 분야의 질문 988개(LLM 생성)를 썼고, 분야를 반으로 나눠 한 번도 보지 않은 분야로 평가했다. CHI 질문을 잘못 거르는 비율을 1%로 맞췄을 때 처음 보는 분야의 질문은 79%를 걸렀다. 직접 쓴 주제 밖 질문 30개 중에서는 29개를 걸렀는데, 예전 12층 모델은 32개 중 12개였다. 짧은 정상 질문 25개 중 잘못 걸린 것은 "deepfake" 하나였다.

정적 모델은 오타에도 약해서, 프로그램에 실제로 나오는 단어로 오타를 고치는 교정기를 넣었다. 어떤 논문에도 없는 단어를 첫 글자가 같고 편집 거리가 1–2인 프로그램 단어로 바꾼다. "hapitc feedbak for virtal reality"는 "haptic feedback for virtual reality"로 고쳐서 찾고, 응답의 `corrected`에 고친 문장을 같이 준다.

## 폰 브라우저에서 돌리기

팀 앱이 웹앱이라 Python 패키지는 폰에서 바로 돌릴 수 없었다. 그래서 추천(retriever), 탐색(explorer), ARC 화면 API를 JavaScript로 옮겼다(`web/`). 패키지와 같은 파일을 읽고, 같은 요청에 같은 응답을 낸다. 테스트 150개(추천 42, 탐색 33, ARC 75)를 Node에서 돌려 Python과 비교하면 인코더 벡터의 코사인이 1.000이고 150개가 모두 같은 답을 낸다. 이 서버 CPU의 Node에서 화면 하나는 1–80 ms(루트 약 20–30 ms)가 걸렸다. 폰에서의 속도는 삼성폰과 아이폰으로 직접 재 봐야 한다.

LLM이 필요해서 서버로 남겨 두려던 기능 중 두 가지도 폰으로 옮겼다. 발표 한 줄 요약과 "Prepare a question"에 쓸 질문 2개는 프로그램이 학회 전에 정해져 있으니, Qwen2.5-7B로 2,777개 발표에 대해 미리 써 두고(`summaries.json`, gzip 0.27 MB) 폰은 찾아보기만 한다.

## 한계

- 서버 모델보다 R@1이 3%p 남짓 낮다. 정확도가 더 필요하면 6층 트랜스포머(23 MB, R@1 0.788, R@8 0.951)로 바꿀 수 있다. `train_light.py --deploy L6 --dim 128`로 다시 만들면 되고, Python과 JavaScript 코드가 둘 다 지원한다. 다만 이때는 `web/vendor/`에 onnxruntime-web(14 MB)을 다시 넣어야 한다.
- 평가 질문도 LLM이 만든 것이라 실제 사용자 질문에서는 숫자가 다를 수 있다. 피드백을 받는 기간에 실제 질문을 모아 다시 재 봐야 한다.
- 주제 밖 판정은 짧은 정상 질문을 가끔 잘못 거른다("deepfake"). 경고만 띄우고 결과는 그대로 보여 주니, 앱에서는 막지 말고 안내 문구로 쓰는 게 맞다.
- 자유 대화(Ask ARC)와 영어가 아닌 언어의 요약은 여전히 LLM이 필요해서 폰에서 돌리지 않는다.

## 다시 만들기

```bash
sbatch scripts/train_light.slurm                                   # 후보 인코더 학습과 비교 (GPU, 약 40분)
python scripts/train_light.py --sweep-w static_d256_d128,L6_d128   # 키워드 비중 다시 맞추기 (CPU)
sbatch scripts/train_light.slurm --deploy static_d256 --dim 128    # 고른 모델을 전체 데이터로 다시 학습
sbatch scripts/gen_offtopic.slurm && python scripts/train_relevance.py   # 주제 밖 판정
sbatch scripts/gen_summaries.slurm                                 # 한 줄 요약과 질문 (GPU, 약 9분)
python scripts/package_model.py                                    # dist/chi2026-retriever (+ web/)
sbatch scripts/eval_ondevice.slurm                                 # 이 노트의 서버 비교
python tests/web_reference.py && node tests/run_web_parity.mjs --encoder   # JavaScript = Python 확인
```
