# 007 발표 Q&A만 서버에 저장한다 (예외 하나)

날짜: 2026-11-20 · 단계: A0 (구현은 A3)

## 결정
- 원칙 "계정·서버 저장 없음"의 **유일한 예외**는 14번 화면의 발표 Q&A다. 익명 질문 글과 그 추천·신고 수만 서버(Upstash Redis, Vercel Marketplace)에 저장한다. 그 밖에는 원칙 그대로: 개인 데이터는 기기에만, 서버는 요청 내용을 로그에 남기지 않는다
- 저장하는 것: `{ id, paperKey, text, createdAt, votes, flags, authorToken(해시) }` 뿐
- 저장하지 않는 것: 이름, 이메일, IP, User-Agent, 위치. 요청 본문은 로그에 남기지 않는다
- 기기 쪽(`arc.device`): Q&A용 기기 무작위 id, 내가 추천한 글 id. 서버로 보내는 것은 그 id의 해시(authorToken)와 추천·신고 대상 글 id뿐
- 보관: **2027-06-13**(CHI 2027 종료 2027-05-14 + 30일)에 전부 지운다. 모든 키에 Redis 만료 시각(EXPIREAT)을 건다. 데모 데이터(chi2026)도 같은 날짜
- 안전: 글 280자, 화면에는 텍스트로만(HTML 이스케이프, `dangerouslySetInnerHTML` 금지), 기기 토큰당 분당 3건·하루 30건, 신고 3번이면 자동 숨김, 추천은 기기 id당 한 번, 내 글은 authorToken으로만 삭제
- 화면: "개인정보를 쓰지 마세요" 한 줄, 빈 상태 "Be the first to ask". 가짜 질문을 미리 넣지 않는다
- 시간이 없으면 기능 플래그로 Q&A 영역을 숨긴다(자를 순서 1번)
- Upstash가 연결되기 전에는 같은 인터페이스의 메모리 저장소로 개발·테스트한다

## 이유
- 질문과 추천 수를 모두에게 보여 주려면 어딘가에 모아야 한다. 기기에만 두면 다른 사람의 질문을 볼 수 없다
- 대회 심사 기준의 데이터 보호 문구: "개인정보를 모으지 않는 게 가장 쉽지만, 많은 솔루션에 필요하다는 걸 이해한다. 무엇을 모으고 어떻게 저장하는지 신경 써 달라" → 모으는 것을 위 목록으로 한정하고 지우는 날짜를 정한다

## 알려진 한계
- **우회 가능**: 기기 토큰은 기기가 스스로 만든다. 저장소를 지우거나 새 프로필을 쓰면 새 토큰이 생겨 분당·하루 제한과 "추천 한 번"을 피할 수 있다. IP를 쓰지 않기로 했으므로 데모 수준의 방어다. 신고 3번 자동 숨김이 마지막 안전장치다
- **URL 로그**: 호스팅의 요청 로그에는 경로(`?paper=<key>`)가 남을 수 있다. 발표 키는 공개 데이터라 개인정보는 아니다. 질문 본문은 POST 본문으로만 보낸다
- 모더레이션 담당자가 없다. 자동 숨김 외의 삭제는 운영자가 Redis에서 직접 한다
